## 2. 🔴 P0 —— 数据安全（强烈建议发布前修复）

### R-01 小说模式是「伪多章」：切章即静默丢弃未保存编辑，保存/关闭只写当前章
- **证据**：`dirtySet` 只记章节索引不存内容（`src/stores/novel.ts:91-92`）；`chapterText` 唯一且仅指当前章，`gotoChapter` 切章时无条件清零并重读磁盘（`novel.ts:320-338`）；`saveChapter` 只按当前章写回（`novel.ts:534-552`）；但 UI 的脏圆点由 `dirtySet` 驱动（`ChapterPanel.tsx:48`、`NovelReader.tsx:233`），呈现"可保存"假象。
- **触发**：编辑第 1 章 → 点「下一章」→ 第 1 章内容从内存永久消失；或编辑多章后关标签点「保存」（`src/stores/tabs.ts:290-296`），只写当前章并整体清空 `dirtySet`，**其它章修改无警告丢失**。
- **同根路径**：外部修改点「重新加载」→ `reloadBook` 无条件 `dirtySet:new Set()`（`novel.ts:276-291`）；「退出小说模式」→ 直接 `unloadBook` 无确认（`tabs.ts:504-513`，对比 `enterNovelMode` 有确认 `tabs.ts:466-482`）。
- **建议**：引入 per-chapter 草稿 `Map<chapterIdx, string>`；切章不改动已编辑章文本；`saveChapter`/关闭/重载 前统一走「保存全部 dirty 章」，并拦截所有清 dirtySet 的出口做未保存确认。

### R-02 关闭窗口无 dirty 拦截：所有未保存修改静默丢失
- **证据**：顶栏红绿灯（`TopBar.tsx:131-137`）与显式按钮（`TopBar.tsx:259-265`）直接 `win().close()`；全工程无 `onCloseRequested`/`on_window_event` 拦截；会话只存路径不存内容（`session.ts:11-15`）；更新安装路径 `utils/updater.ts:126-127` 触发 `install_update` 后直接 `app.exit(0)`，同样强杀 dirty 标签。
- **建议**：Rust 侧注册 `onCloseRequested` 并 `prevent_close`，发事件给前端跑 `saveAll` 或弹「保存/不保存/取消」后再真正关闭；更新安装前先 `saveAll`。

### R-03 保存非原子：保存窗口期内输入的文字被静默丢弃
- **证据**：普通标签 `updateContent` 在 `saving` 态直接 return（`tabs.ts:253`）；小说 `saveChapter` 无 editing/saving 锁（`novel.ts:534-602`），大章保存期间 contenteditable 仍可输入（`NovelReader.tsx:110-116`），写盘后 `origText:cur.chapterText` + `dirtySet:new Set()`（`novel.ts:567-569`）+ `setNovelDirty(false)`（`tabs.ts:295`）——保存窗口内输入的内容既未上盘又被清脏。
- **建议**：保存开始即锁定/置 editing，或做冲突检测：保存起点 `chapterText` 快照与结束时比较，不一致则不置 ready 并提示重存。

### R-04 大章保存期间切章：章节错写/写空的竞态
- **证据**：`saveChapter` 捕获 `ch` 后 `await ensureFullChapter`（`novel.ts:537-540`）无互斥（对比 `loadMore` 有 `paging:true` 守卫 `novel.ts:379`）；期间切章后 `gotoChapter` 已重置 `chapterText`（`novel.ts:320-338`），`saveChapter` 再取 `b2.chapterText` 读到新章文本，却按旧章 `start/end` 写回——新章内容写入旧章区间致文件损坏；`ensureFullChapter` 与 `loadMore` 并发还会双重 append。
- **建议**：`saveChapter` 全程锁定目标章；保存结束校验 `chapterIdx` 未变，变了则拒绝写；`ensureFullChapter` 复用 `loadMore` 的加载互斥。

## 3. 🟠 P1 —— 安全（建议尽快修复）

### R-05 `csp:null` + `assetProtocol.scope:"**"`：WebView 全盘可读、零纵深防御
- **证据**：`src-tauri/tauri.conf.json:28-33`。`convertFileSrc` 产出 `http://asset.localhost/<任意绝对路径>`（`src/utils/mdImage.ts:33`、`ImageViewer.tsx:105`）可读整个文件系统；而本应用核心场景是打开**不可信的外部 .md/.txt**。当前未见已证实的 md→JS 通道（Milkdown 无 html 节点、链接有 sanitize-href），但 `csp:null` 使任何未来渲染 gadget（KaTeX XSS、ImageBlock、SVG/data 路径）一旦出现即可直接持有 `window.__TAURI_INTERNALS__` 全能力，无任何纵深。
- **建议**：设严格 CSP（`default-src 'self'; script-src 'self'; img-src 'self' asset: data:; connect-src 'self' asset:`），asset scope 从 `"**"` 收窄为"随打开目录动态注册的子树 allowlist"（路径前缀匹配）。多子智能体一致将此项列为最高优先级安全项。

### R-06 更新命令构成「任意文件写入 + 任意程序执行」原语，服务端零约束 + 信任链同源
- **证据**：`write_update_chunk(path, b64)` 写任意路径（`updater.rs:105-119`）；`download_file(url, dest)` 落任意位置（`updater.rs:248-251`）；`install_update(path)` 直接 `Command::new(path).arg("/S")` 后无条件 `app.exit(0)`（`updater.rs:153-172`）。前端 `destPath` 拼入**远端清单返回的 version**（`utils/updater.ts:94-95`），含 `..` 时可穿越 update 目录。信任链：清单与安装包同 GitHub 同源（`utils/updater.ts:13-14`），SHA-256 只防破损不防"仓库/账号被接管"，**无 Authenticode 签名校验、无回滚、安装失败无恢复**。
- **建议**：Rust 侧对 path/dest 做 canonicalize + 前缀断言（必须位于 `prepare_update_dir` 返回值下且扩展名 `.exe`）；发布侧对 latest.json 内嵌签名，客户端用内置固定公钥验签后再采信 version/url/sha256；安装前验证安装包签名者；安装成功写版本标记、保留旧 exe 支持回滚；`install_update` 改为轮询安装结果后再退出。长期建议整体迁移官方 `tauri-plugin-updater`。

### R-07 IPC 面过大：任意路径读写/删除/重命名，删除为永久删除（无回收站）
- **证据**：`read_text_file/write_text_file/create_file/delete_path/rename_path/read_dir_entries`（`fs.rs:237-367`）对 path **无任何作用域校验**（Tauri 自定义命令不经 capabilities 过滤，`capabilities/default.json:6-17` 只列 core/dialog/opener）；`delete_path` 用 `remove_dir_all`/`remove_file` **永久删除**（`fs.rs:348-355`，注释自称"M3 换 trash crate"至今未落地）；`rename_path` 的 `new_name` 未过滤 `\` 与 `..`（`fs.rs:362`）可移出父目录。
- **建议**：写类命令在 Rust 侧校验 canonical 路径位于当前打开的 rootPath（前端 `openRoot` 登记到 State）之下；删除改走回收站（`trash` crate）；rename 拒绝含路径分隔符的输入。

### R-08 `create-webview-window` 全局放行：`workspace-*` 窗口继承全部权限
- **证据**：`capabilities/default.json:13` 放行 `core:webview:allow-create-webview-window`，windows 域覆盖 `workspace-*`（`:5`）；`openWorkspace.ts:13-25` 正常新建窗口，但脚本同样可 `new WebviewWindow("workspace-x", {url: 任意})` 获得应用同等待遇（删除/下载/安装全命令），或造同源页面从 `?root=` 分流继续触发 R-05 链路。
- **建议**：为 workspace 窗口建最小能力集（仅 读/列举），`create-webview-window` 移出 default、改为 Rust 侧显式创建并校验 url 以自身 index.html 为前缀。

### R-09 不可信文档自动外联 + 启动固定外联请求
- **证据**：md 中 `https?:`/`data:` 图片直通不处理（`mdImage.ts:29`），Crepe 渲染后直接发请求暴露 IP/指纹；`[link]` 经 `opener:allow-open-url`（`capabilities/default.json:16`）拉起浏览器；主窗口启动 2.5s 后自动 fetch 固定清单地址（`App.tsx:229-245`，`autoCheckUpdate` 默认开）。
- **建议**：远端图默认占位 + 点击加载、`referrerpolicy="no-referrer"`；启动检查延后到空闲期或默认关。

## 4. 🟠 P1 —— 正确性与并发（建议尽快修复）

### R-10 UTF-16 编码写回不保真：无 BOM 文件保存后被强制加 BOM；novel 侧 UTF-16 扫描整条路径失效
- **证据 A（写回）**：`encode_text` 的 `UTF-16 LE/BE` 分支**无条件写 BOM**（`fs.rs:175,182`），忽略 `has_bom`（对照 UTF-8 分支显式判断 `fs.rs:168`）；而 `detect_encoding` 对无 BOM 的 UTF-16 文件返回 `("UTF-16 LE", false)`（`fs.rs:112-113`）。一个无 BOM 的 UTF-16 文件编辑保存后凭空多 2 字节 BOM。
- **证据 B（扫描）**：`novel.rs:434` 对 `UTF-16 BE` 也一律 `UTF_16LE.decode`（字节序反转全乱码）；`scan_utf16_str` 字节偏移按 `line.len()*2` 估算错（`novel.rs:468`，line.len() 是 UTF-8 字节数）；BOM 未剥导致首章标题 `strip_prefix('第')` 失败漏检（`novel.rs:434`）。
- **建议**：UTF-16 分支 `if has_bom { 写 BOM }`；novel 扫描按 encoding 选 LE/BE 解码器并先跳 BOM；偏移按 UTF-16 code unit 数累计；补 LE±BOM / BE±BOM 四组 fixture 集成测试。

### R-11 IPC 边界未校验：`read_chapter` 可致超大分配/OOM；`write_chapter` 无 start<end 校验可损坏文件
- **证据**：`read_chapter` 直接 `vec![0u8; (end-start) as usize]`（`novel.rs:547-548`），未与文件长度比对，越界参数秒级分配百 MB~GB → `memory allocation failed` 全局 abort；`write_chapter_impl` 未校验 `start < end`（`novel.rs:585`），`start>end` 时区间复制两遍写出损坏内容并覆盖原文件（`novel.rs:590`）。
- **建议**：先取 `metadata().len()` 做 `start/end` 钳制；写入口校验 `start < end && start <= len`，否则返回错误**不写盘**。

### R-12 watcher 并发缺陷：多窗口同目录被幂等短路 + 事件风暴下 stop 不生效/重挂双 watcher
- **证据**：`start_watch` 幂等只按 path（`watcher.rs:74-76`）——第二个窗口打开同目录不建立自己的 watcher，owner 窗口关闭后**另一窗口永久断更**（`watcher.rs:136-145`）；`watch_loop` 只在 recv 超时分支检查停止条件（`watcher.rs:120-129`），高频事件目录下 `stop_watch` 不生效；stop→start 同路径时旧线程 `is_current_root` 按路径匹配新条目，产生双 watcher 重复事件；所有锁 `unwrap()`，锁内 panic 会毒化互斥体致级联崩溃。
- **建议**：幂等键改 `(window label, path)`；主循环 `try_recv` 收满一批立即 flush、再用 `recv_timeout` 兜底检查停止；`is_current_root` 按 (label,path) 判定；锁做 poison 恢复。

### R-13 external-changed 分叉状态不保留：提示期输入一个字符即覆盖"磁盘已分叉"事实
- **证据**：`updateContent` 无条件把 `external-changed` 置回 `dirty`（`tabs.ts:255`），提示条消失（`App.tsx:262-264`），稍后 Ctrl+S 直接覆盖外部改动全程无警告。
- **建议**：`TabDoc` 增加持久布尔 `externalModified`，输入不清除；保存时若为真先弹「磁盘版本已变化，确认覆盖？」。

### R-14 dialog 模块级单例：并发两个确认框时前一 Promise 永不 resolve，标签关闭卡死
- **证据**：`showDialog` 用单变量 `pendingResolve` 无队列（`dialog.ts:35-43`），后打开的覆盖前者（`dialog.ts:46-52`）。两个 dirty 标签快速连续触发关闭确认，第一个 `close()` 的 `await`（`tabs.ts:227-231`）永久 pending。
- **建议**：改为请求队列 + 唯一 id，`answerDialog` 带 id 精准 resolve。

### R-15 contenteditable + innerText 往返改写空白结构
- **证据**：编辑按行建 `<div>textContent</div>`（`NovelReader.tsx:425-434`），读回 `innerText.replace(/\u00a0/g," ")`（`NovelReader.tsx:114`）——连续空格折叠、行首缩进丢失、尾空行变化、非断空格被替换；阅读渲染另用 trim+filter（`NovelReader.tsx:207-213`），保存即永久改写空白。
- **建议**：弃用 innerText：基于 caret 的前后端串接，或按 `<div>` 逐个取 `textContent` 显式重建空行；不要替换 `\u00a0`。

### R-16 其它低危正确性项
- **R-16a** `write_chapter` 在 `start==0 && has_bom` 时无条件插 UTF-8 BOM 字节（`novel.rs:576-578`），与目标编码无关；手动指定编码路径强制 `has_bom=false`（`novel.rs:421`）会使原 BOM 丢失 → 按 encoding 选 BOM 序列、has_bom 由扫描回填。
- **R-16b** `write_text_file`/`write_chapter` 均为直接 `fs::write` 覆盖（`fs.rs:268`、`novel.rs:590`），崩溃/断电留截断文件 → 同目录写 `.tmp` + `rename` 原子替换，成功后再 `register_saved`。
- **R-16c** `check_webview2`（`lib.rs:97-115`）对非 Windows 平台必然返回 false → 跨平台构建"能编译不能跑" → 加 `#[cfg(not(windows))] return true`。

## 5. 🟢 P2 —— 性能与可扩展性

### R-17 非小说大文件无大小上限：整读 + 解码 + JSON IPC + 前端整串驻留，峰值内存达磁盘数倍
- **证据**：`read_text_file` 整读（`fs.rs:239`）→ 全量解码（`fs.rs:244`）→ JSON IPC 回传 → store 整存（`tabs.ts:142,199`）→ CM6 整 doc（`CodeEditor.tsx:43-45`），同一数据多份拷贝。M8 已移除 5MB 只读，`readonlyReason:"large"` 分支成死代码（`tabs.ts:42/70/156/188` 只会被置 `"disk"`）。
- **触发**：500MB+ 的 log/txt（普通模式）秒级阻塞 + 数 GB 峰值 RSS，无提示无保护，直接击穿 design §8「>5MB 保护」两条验收。
- **建议**：恢复超阈值（如 8MB）→ 只读或懒加载分块；至少加"文件过大，将占用大量内存"确认。

### R-18 章节扫描"流式不进内存"名不副实
- **证据**：`scan_chapters` 用 `fs::read` 整文件读入（`novel.rs:412`），为 M8 修复须把全量字节喂 `detect_encoding`（`novel.rs:421-423`）。流式只省了解码 CPU，没省内存；500MB~2GB 小说打开瞬间吃整个文件大小 + 解码副本。
- **建议**：检测改"头部 64KB + 中后部采样"（解决纯 ASCII 头问题），正文用 `BufReader` 按行流式喂给现有字节切行逻辑，或 `memmap2` 内存映射；1GB fixture 下验证峰值 RSS。

### R-19 标签 content 全量常驻、无 LRU；「20 标签 <300MB」可被击穿
- **证据**：`TabDoc.content` 只到 close 才释放（`tabs.ts:24`）；`updateContent` 每次按键生成整串并映射全量 tabs（`tabs.ts:250-262`）；design §7.5 的「>12 标签释放旧文档」无实现。会话恢复逐本整读（`App.tsx:155-160`）。
- **建议**：设置打开标签数上限 / 大文件仅存元数据 + 显示侧热加载（复用 novel 懒加载思路）。

### R-20 design 自认的"最关键性能坑"——raw IPC / stream 协议——从未落地
- **证据**：design §7.2 明确要求大文本走 raw IPC 或 stream 协议，但 grep 全仓无 `tauri::ipc::Response` / 自定义协议；`read_chapter` 仍返回 `Result<String,String>`（`novel.rs:545`），几十 MB 全走 serde_json 全量序列化。
- **建议**：`read_chapter` 等大文本命令改返回 `tauri::ipc::Response`（原始 bytes）或注册 `stream://` 协议。

### R-21 每个 .txt 打开做两次整读 + 两次全量编码检测
- **证据**：`openFile` 对 .txt 先 `scan_chapters`（整读 + 全量 detect），判定非小说后又 `read_text_file` 再整读（`tabs.ts:173-197`），scan 结果（encoding/eol）被丢弃；`fs.rs:120` `feed(&bytes, true)` 全量喂入，与注释"只喂头部 64KB"不符。
- **建议**：非小说 .txt 把 scan 结果直接复用（或先读一次，根据 is_novel 决定走小说/普通，避免二次读取）。

### R-22 入口 chunk 仍含 CodeMirror 6 核心（~572KB raw / 185KB gz）
- **证据**：入口 `index-CHHDu2LK.js` 含 `@codemirror/view` 特征（`contenteditable`），其余懒加载 chunk 无此标记；根因 `utils/language.ts:4` 对 `@codemirror/language` **值导入**（LanguageSupport/StreamLanguage，依赖 view+state），经 `tabs.ts:9 → App.tsx` 进静态入口图；`vite.config.ts` 无 `manualChunks` 手动分包（design §7.1 承诺未实施）。Milkdown 1114KB 是懒加载的 ✅。
- **建议**：语言包入口改 `import type` + 动态 `await import` 后再取支持；vite 手动分包把 CM6 移出首屏。

### R-23 事件风暴下目录树每条事件 O(N) 全树递归 + 每事件一次目录重列；watcher 未在源头过滤噪音目录
- **证据**：每个 fs-event → `findNode` 全树递归（`tree.ts:189-197`）→ 命中已加载层再 `refreshDir`（每文件 metadata 句柄 `fs.rs:309-313`）+ `patchNode` 全树拷贝（`tree.ts:199-217`）+ `flattenTree` 全量重渲；`watcher.ts:25-28` 逐条处理无合并；事件源 `RecursiveMode::Recursive` 对 node_modules/.git 不设防（`watcher.rs:84`）。
- **建议**：Rust 侧按 300ms flush 对同目录事件聚合去重 + 源头忽略噪音目录（把 `read_dir_entries` 的过滤逻辑下沉到 flush）；前端按父目录合并一次刷新。

### R-24 小说"整本单章"（无章节 txt）无虚拟化：全量 DOM + 编辑态每行一个 DOM
- **证据**：无章节 txt 阅读模式虚拟成"全文"单章（`novel.ts:212-215`），`loadMore` 渐进 append（`novel.ts:397-407`）→ 整章 DOM 全驻留且每块全量重建；`ensureFullChapter` 把全书灌满内存（`novel.ts:412-444`），编辑逐行建 `<div>`（`NovelReader.tsx:429-433`）。
- **建议**：阅读视图对长单章做内容虚拟化（仅渲染视口段落 + 上下缓冲），编辑态同样虚拟化。

### R-25 `read_dir_entries` 对每个文件 `metadata()` 取大小：万级目录展开是万次句柄级系统调用
- **证据**：`fs.rs:309-313`。Windows 上 `DirEntry::metadata` 需打开句柄而非复用 FindFirstFile 的体积字段；叠加排序（`fs.rs:327-329`），万级小文件目录可能超 §8「1 万文件 <500ms」。
- **建议**：树节点读目录时仅对文件按需取大小，或改为异步/分批取。

## 11. 结论

简阅是一款**完成度很高、架构清晰、可正常交付的个人级产品**——"比记事本强、比 VS Code 轻"的定位基本兑现，编码检测/章节解析/测试覆盖是其明显强项，尤其 UTF-8/GBK 圆整与 50MB 扫描基准这类"硬核"细节体现了作者的工程能力。

风险集中在**边界数据安全**（小说多章保存、退出提示、删除方式）与**安全纵深**（CSP/asset 作用域/更新信任链/IPC 面）。这些问题不影响日常轻量使用，但作为一款每天打开不可信文档（任意 .md/.txt）的编辑器，"数据永不静默丢失"与"WebView 假设可被攻破"这两条底线值得在 1.0 之前补上。**修复 R-01/R-02 两项 P0 后，即可放心日常使用。**
